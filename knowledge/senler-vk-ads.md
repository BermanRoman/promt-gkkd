# Senler и VK Реклама: сборка бота-квиза и лонча, реклама с переходом в сообщения

**Для кого:** Агент Senler (`agents/14-senler.md`, разделы 2, 3, 5–7), Агент рекламы ВК (`agents/13-vk-ads.md`, разделы 3–7), Конструктор бота (`agents/08-bot.md`, сценарий бота; платформенную сборку в Senler выполняет Агент Senler) и Фиксик, когда бот собирается в Senler, а трафик идёт из VK Рекламы. Это инструментальная методичка: что говорить в квизе и лонче — по `knowledge/quiz.md`, `knowledge/dramaturgy.md`, `knowledge/follow-up.md`; здесь только как собрать, выложить и проверить. Адаптером по умолчанию остаётся Multy (`knowledge/multy.md`); для Senler и VK действует этот файл.

## 1. Когда применять и границы

- Бот живёт в Senler (ВКонтакте), реклама ведёт на подписку или в сообщения сообщества.
- Это внешние кабинеты. Запросы веб-кабинета Senler и GraphQL VK Рекламы не документированы и могут меняться: перед массовой операцией сверь формат на одном шаге или одном объявлении, при расхождении иди по текущему интерфейсу.
- Действия в аккаунтах — только по поручению автора. Создание и публикация кампании, публикация и запуск ботов, тексты объявлений, выкладка файлов в публичный репозиторий — отдельные явные разрешения; разрешение на одно не покрывает другое.
- В проектных файлах нет секретов, токенов, паролей и реальных ID клиента. ID в примерах ниже — формат: `<id>`.
- Живой прогон в ВКонтакте с тестовым аккаунтом остаётся отдельным шагом: целостность по API не доказывает, что человек получит сообщения.

## 2. Senler

**Запросы редактора.** Скрипт запускается во вкладке кабинета, CSRF берётся из `meta[name=csrf-token]`, заголовок `X-Requested-With: XMLHttpRequest`:

- `/ajax/cabinet/bot/<bot>` — чтение бота (все шаги);
- `/ajax/cabinet/botStep_add/<bot>` `{item}` — добавить шаг; `botStep_update/<bot>` `{step_data}` — обновить; `botSteps_delete/<bot>` `{step_ids}` — удалить;
- `/ajax/cabinet/botStepConnections_update/<bot>` `{connections:[{source_data, target_data}]}` — связи, пачками по 40;
- `/ajax/cabinet/upload_image/<group>` (form: `file`, `crop`) — картинка в хранилище Senler → `file_id`, `url`, `preview`.

**Шаги.** Сообщение — `parts[{type:'message', text, quill_delta}]` и `buttons[{id,title,type:'text',color,row,sort}]`; карусель — `template:{type:'carousel', elements:[{id(uuid), title, description, action:{type:'open_photo'}, file_id, photo_link, preview}]}`, кнопка карточки связана через `template_item_id`. Действие — `parts` из `variable/set`, `activity/typing`, `bot_id/add|del`, `subscription_id/add`. Условие — `contain:'dispatcher'`, `parts:[{type:'default'}, {type:'case', operator, conditions}]`.

**Особенности.**

- Новый бот создаётся с пустым «Сообщением»: сборщик удаляет его первым.
- Условие без единого кейса не сохраняется; «Добавить в бота» без шага сохраняется с ошибкой «Выберите шаг» (нужны `step_id` и `step_title`).
- Связи условий. Ветка N: `source_data:{item_id, dispatcher_part_connect:N}`, «Иначе»: `dispatcher_otherwise_connect:0`. Кнопка: `button` и `button_id`. Обычный шаг: без доп. полей. Поле `connect` для условия сервер хранит, но редактор не рисует.
- Лимит веток в одном условии около 10. Длинный список режь цепочкой по 8: «Иначе» ведёт в следующее условие. Для разводки по UTM — ветки `utm_content = <номер объявления>` с `operator:'or'`, «Иначе» ведёт в бот по умолчанию.
- Сравнение `in` — вхождение подстроки: длинные ключи ставь раньше коротких, иначе `inner` перехватит `inner_hidden`.
- Ключ бота — до 6 латинских заглавных букв.
- «Добавить в бота» из другого бота ссылается на шаг по `master_id` опубликованной версии, а не по черновому `_id` (см. раздел 7, п. 2). Приветственного бота публикуй до того, как квизы начнут на него ссылаться, и сразу перечитай ссылки.
- Таймер: `contain:'timer'`, `delay:'day'|'hour'|'min'|'sec'`, `delay_value`. Серия по будням в заданное время: `time_in:'in'`, `time:{h,m}` (время МСК, пересчитай на пояс аудитории), `week:[1,2,3,4,5]`. Окно «с — до» — `time_in:'period'`, `time:{from_h,from_m,to_h,to_m}`.
- Переменные. Системные пишутся как есть: `%username%`, `%fullname%`, `%city%`, `%utm_content%`, полный список — справка Senler «Стандартные переменные». Пользовательские — `{%имя%}`, создаются запросом `VarLeadSave` до использования. Сборщик не должен превращать системные в пользовательские.
- Публикация. Правки шагов — черновик до «Опубликовать» (`bot_publish`), включение — «Запустить» (`bot_activate`). Оба действия — до старта рекламы.

**Серия лонча.** Цепочка: `Отметка: прошёл → Таймер 1 → Серия 1 → Таймер 2 → …`; в сериях кнопка «Неактуально» ведёт в общий блок «Стоп» (без кнопки в последней). Старые цепочки удаляются перед сборкой, имена шагов `Лонч · N · название` и `Таймер лонча N` дают поиск и повторную сборку без дублей.

**Картинки в серии.** Файл грузится через `upload_image` (FormData), в первую часть сообщения кладётся вложение `parts[0].attachment: [{type:'photo', url, preview, file_id}]`. Для Senler хватает JPG около 1280 px по длинной стороне.

**Подписная страница группы.** Название, иконка, баннер, описания, кнопка. Сохраняй её запросом `edit_subscription` целым JSON-ом: возьми текущий объект из `getSubscription`, измени нужные поля, отправь со всеми полями (со слов автора, в журнале сборки не проверено — сверить перед действием). До и после сделай diff. Переменные на подписной не ставь: неподписанный посетитель и модератор их не увидят подставленными.

**Раскладка блоков.** Блоки кладутся по координатам `top/left`; карусели и результаты в редакторе выше и шире, чем кажется:

1. после сборки открой редактор и измерь реальные размеры блока вместе с потомками (карусель вытягивается лентой вправо, высота до сотен пикселей);
2. раздели измеренное на масштаб редактора (сохранённый zoom, например 0,85, ломает расчёт);
3. сдвинь столбцы по максимуму правого края всех потомков плюс запас, блоки в столбце — по реальной высоте плюс отступ;
4. проверь перекрытия: ноль, число связей не изменилось.

Раскладку повторяй после каждой сборки и пересборки.

## 3. Доставка файлов в кабинеты

Встроенный браузер, из которого идут скрипты, изолирован: CSP кабинетов Senler и VK блокирует fetch, img и iframe к localhost, буфер обмена в страницу не передаётся, всплывающее окно открывается в той же вкладке. Варианты:

1. **Автор сам загружает** файлы (например, перетаскивает баннеры в Медиатеку VK), агент собирает объявления из загруженного.
2. **Временный публичный репозиторий** — только по явному разрешению автора, и только для материалов без персональных данных и данных клиента (картинки серий, тексты лончей без имён). Страница кабинета берёт файлы с `raw.githubusercontent.com` и загружает в `upload_image`. Сразу после загрузки репозиторий удаляется: нужен scope `delete_repo` у `gh`, проверь его заранее, иначе удаление упрётся в права (со слов автора, в журнале сборки не проверено — сверить перед действием). Локальная копия остаётся.
3. **JSON и тексты** — тем же репозиторием либо частями через `javascript_tool` со сверкой длин (суммарная длина и число элементов до и после).

Данные между перезагрузками страницы держи в `sessionStorage`, не в переменных страницы.

## 4. VK Реклама

- **Доступ.** Агентский кабинет: REST и GraphQL с параметрами `account=<id>&sudo=<id>`; прямой GET GraphQL требует заголовков `apollo-require-preflight` и `X-Target-Sudo`. Проще и надёжнее вызывать мутации через клиент страницы `window.__APOLLO_CLIENT__`; перехват `mutate` показывает документ нужной мутации.
- **Кампания и группа.** Цель «подписка на сообщество» (subscribe), ссылка — подписная страница Senler с автоподпиской, UTM `utm_content={{banner_id}}`. До проверки автором кампания остаётся черновиком.
- **Объявления пачкой.** Мутация `UpsertDrafts`: `drafts.create.ads` с `parentKey` = ключ группы, а группа обязательно перечислена в `drafts.update.groups`, иначе `campaign_draft_id` придёт `null`. Запросом `AdPlanDraftById` прочитай созданное и сверь с картой объявлений: число, заголовки, тексты, кнопки.
- **Креативы.** Слоты принимают точные размеры: `image_600x600`, `image_1080x607`. Оригиналы из Медиатеки (например 1080×1080, 1536×864) редактор отклоняет при публикации. Ужми в странице canvas-ом, загрузи `POST /proxy/mt/v2/content/static.json` (file и `data {width,height}`), подставь `UpsertDrafts`-ом.
- **Автодобавки.** VK сам добавляет обрезки 4:5 и 9:16 и автовидео: убери или загрузи свои форматы. Сам нарезай баннер под 16:9 и 1:1; 4:5 срезает надпись.
- **Форма объявления.** Файл во вложение — через React-обработчик `onInput` скрытого `input[type=file]`, обычный `change` не срабатывает.
- **Текст.** Кнопка «Подробнее» (`learnMore`); порядок чтения — картинка, заголовок, текст, кнопка. Объявление продаёт следующий шаг (разрешение написать), а не визит.
- **После публикации.** `banner_id` известны только теперь: впиши их в ветки разводки приветственного бота и опубликуй его. Статус модерации (`pending`) и активность проверяй отдельно.

## 5. Картинки серий и баннеров через Codex

- Команда: `codex exec --skip-git-repo-check -s read-only -i героиня.png -`, промт со stdin; результат Codex кладёт в каталог сгенерированных изображений сессии, скрипт находит свежий PNG по `session id` из вывода.
- Образец героини (одно изображение) прикладывается к каждой генерации: во всех баннерах и сериях одна и та же женщина. Задание — «на картинке именно эта женщина, одежда и поза — по сцене».
- Заголовок серии — единственный текст на картинке (исключение из общего правила «генератор не пишет текст», `decisions.md`, §36, п. 5), крупно, по-русски, читаемо на телефоне; никаких вывесок, логотипов и брендов.
- Несколько сессий параллельно (по 5 сразу); готовые файлы пропускаются, перерисовка нужных — `--only 3,7`; правка в том же разговоре — `codex exec resume <session> -`.
- Запуск скриптов с `python3 -I`: соседний модуль не виден, добавь папку скрипта в `sys.path` (раздел 7, п. 10).
- Нарезка под слоты — ImageMagick (`magick -crop … -resize …!`). Размеры проверяй по файлам, не на глаз.
- Модель и режим Codex берутся из его локального конфига; не фиксируй их в методичке.

## 6. Порядок выпуска

1. Квизы собраны, целостность проверена, раскладка 0 перекрытий.
2. Лончи собраны, картинки прикреплены (число серий и вложений совпало).
3. Приветственный бот собран, опубликован; все боты опубликованы и запущены.
4. Кампания создана черновиком, креативы нужных размеров, публикация по разрешению автора.
5. После публикации: `banner_id` в разводку, приветственный бот опубликован повторно, ссылки «В меню» перечитаны, живой тест.

## 7. Ошибки и как их избежать

| № | Симптом | Причина | Как избежать / проверить |
|---|---|---|---|
| 1 | Ветки условия не рисуются в редакторе, бот может не пройти дальше условия | Связь создана полем `connect`: сервер хранит, редактор не понимает | Для условий — только `dispatcher_part_connect: N` и `dispatcher_otherwise_connect: 0`. Проверка: число связей в отрисованном редакторе равно числу в сборке |
| 2 | В «Добавить в бота» вместо шага «[Удалено] Меню» | Ссылка на черновой `_id`, после публикации нужен `master_id` | Публиковать целевой бот до сборки ссылок, брать `master_id`. Проверка: поиск «[Удалено]» по редактору сразу после публикации |
| 3 | Блоки налезают друг на друга | Высоты и ширины заложены на глаз; карусели мерили по рамке без потомков; не учтён масштаб редактора | Мерить в редакторе с потомками, делить на масштаб, сдвигать по краю потомков. Проверка: 0 перекрытий после каждой сборки |
| 4 | Реклама ведёт в пустую или неработающую воронку | Боты остались черновиками, не опубликованы и не запущены | `bot_publish` и `bot_activate` до старта рекламы. Проверка: список ботов, статусы «активен» |
| 5 | Публикация кампании падает (`ad.field.content_image_600x600`, десятки ошибок) | В слоты поставлены оригиналы Медиатеки неподходящего размера | Ужать до точных 600×600 и 1080×607 и залить через `content/static`. Проверка: чтение черновика и пробная публикация, число ошибок 0 |
| 6 | Правки объявлений пропадают или публикация идёт со старым | Публикация из редактора после создания объявлений через API использует устаревшее состояние страницы | Перезагрузить редактор, потом публиковать (со слов автора, в журнале сборки не проверено — сверить перед действием). Проверка: открыть, сверить число и тексты с картой |
| 7 | Данные и сборщики пропали | Навигация или перезагрузка вкладки очищает память страницы; фоновый скрипт оборван переходом той же вкладки | Хранить в `sessionStorage`, не вести навигацию во вкладке с работающим скриптом |
| 8 | Файлы не доходят до кабинетов; репозиторий не удаляется; агент сделал лишнее | Браузер без доступа к localhost, нет буфера; не проверен scope `delete_repo`; разрешение на одно действие принято за разрешение на другие | Раздел 3; права агента на создание и публикацию и тексты объявлений согласовывать отдельно; `delete_repo` проверить до выкладки (со слов автора, в журнале сборки не проверено — сверить перед действием) |
| 9 | Подписная страница: пустое название, потеряны поля | Подписная сохранена из HTML-формы или частичным JSON | `edit_subscription` целым JSON со всеми полями `getSubscription` (со слов автора, в журнале сборки не проверено — сверить перед действием). Проверка: diff до и после, перечитать через `getSubscription` |
| 10 | Скрипт с `python -I` не находит соседний модуль | `-I` убирает папку скрипта из `sys.path` | `sys.path.insert(0, str(Path(__file__).resolve().parent))` в начале |
| 11 | Тексты лонча: советы в лоб, противоречия сроков и цифр между сериями, в кульминации непроверенная покупка, не отмечена собирательная героиня | Серии писались порознь, без общего брифа и холодного чтения | Проверка по действующим `knowledge/texts.md`, §3 и `knowledge/dramaturgy.md`, три круга Клиента мечты, скрипт-проверка формы |

**Общий принцип.** После каждой массовой операции проверяй результат по API и в отрисованном редакторе (число серий, вложений, таймеров, связей, перекрытий, объявлений), а не по ответу `success`: сервер принимает то, что редактор потом не показывает.

**Журнал сборки.** Дата, действие, объект (`<id>`), ожидаемое и наблюдаемое, ошибки и исправления; без секретов и данных клиента. Состояние «собрано», «опубликовано» и «проверено в ВКонтакте» отмечай отдельно.
