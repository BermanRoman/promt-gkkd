# Multy: возможности, ограничения и браузерная сборка

**Для кого:** Конструктор бота и Фиксик. Это адаптер платформы к `knowledge/bot.md`, `core/handoff.md` и карте проекта. Методика определяет поведение, справка Multy — доступные средства, журнал сборки — фактически проверенный результат.

**Проверено 01.11.2026.** Пройдено объединение 713 адресов официального sitemap и 725 уникальных адресов навигации: 730 адресов, без ошибок извлечения текста. Это полный текстовый обход обнаруженной справки, а не проверка всех функций в аккаунте. Иллюстрации и видео всех статей не просматривались; параметры, показанные только на них, не восстановлены по догадке. При изменении интерфейса сначала прочитать текущую официальную статью, затем сверить экран аккаунта.

Статусы ниже:

- **Подтверждено справкой** — функция описана на официальной странице; работоспособность в конкретном проекте ещё проверяется.
- **Решение сборки** — наша комбинация подтверждённых средств; это не готовая функция Multy.
- **Не найдено** — в доступном тексте нет подтверждения. Это не утверждение, что функция отсутствует.
- **Не проверено** — нужен аккаунт, выбранный тариф или прогон через подключённый мессенджер.

## 1. Термины и модель исполнения

**Проект** объединяет интеграции, пользователей и автоматизацию. **Интеграция** — подключение конкретного бота, сообщества, платёжного аккаунта или ИИ-провайдера. **Блок-схема** — граф блоков со стрелками. **Ветка** начинается событием и продолжается соединёнными блоками. Это не отдельный объект «цепочка рассылки», который следует искать в меню.

В редакторе есть блоки «Событие», «Условие», «Сообщение», «Таймер», «Действие», «Примечание». Внутри блока выбирается **контейнер** — конкретная функция. Событие с несколькими контейнерами срабатывает по любому из них. В условии контейнеры проверяются по порядку; при отсутствии совпадения работает «Иначе». Действия и таймеры внутри блока исполняются последовательно. Стрелки могут запускать параллельные направления: приоритет `/stop` > оплата > передача человеку нужно построить явно, он не возникает из расположения блоков.

Блок добавляется через нижнюю левую панель, контекстное меню полотна или вытягивание стрелки из выходного порта. Соединение: выходной порт первого блока → входной порт второго. Стрелку можно выделить и удалить; сначала сверять, что выделено.

## 3. Поля, переменные, списки

Постоянные сведения клиента хранить в **полях профиля**, а не во временных переменных. «Поля профилей» → «Создать» → название → тип → уникальное системное имя латиницей без пробелов → «Сохранить». Значение читается как `{field:system_name}`. Для изменения есть действия «Задать значение текстового поля», «Задать значение числового поля», сохранение даты/времени, массива и объекта. Не менять системное имя после сборки: его потребуется заново выбрать в действиях.

В `build-scheme.md` обязательна таблица соответствий **для каждого поля, списка, временной переменной и события проекта**: логическое имя из карты/`core/glossary.md` → постоянное поле / список / временная переменная / строка журнала → реальное системное имя → тип → начальное значение → источник значения → кто и по какому событию меняет. Русские логические имена не переименовываются: таблица связывает две нотации. Пока строка не заполнена, узел не готов к сборке. Пример **решения сборки**, не обязательные имена платформы:

| Имя методики | Системное имя | Хранение |
|---|---|---|
| состояние | `funnel_state` | текстовое поле |
| оплачено | `paid_status` | число 0/1; отдельно заказ и продукт |
| стоп | `stop_reason` | текстовое поле; пусто / отписка / не_подходит / другая причина из карты |
| передан_эксперту | `human_handoff` | число 0/1 |
| единиц_потреблено | `units_consumed` | число |
| окно_до | `offer_deadline` | дата и время |
| история | `ai_history` | JSON-массив |
| события покупки | `purchase_id`, `purchase_product` | текст/число по данным реального провайдера |

Для примеров выше источники и владельцы изменения тоже обязательны: `funnel_state` меняет сервис по переходу карты; `paid_status` и поля покупки — обработчик подтверждённого платежа; `stop_reason` — обработчик стопа/отказа, снятие ограничительного стопа только человеком по правилам карты; `human_handoff` — передача и явный возврат человеком; `units_consumed` — обработчик уникального действия единицы; `offer_deadline` — сервис из реального согласованного условия; `ai_history` — сборщик истории после входящего/служебного сообщения и ответа ИИ. Начальные значения задаются проектом, например 0 для счётчика/флага и пустое значение для незаданного срока, а не выдуманная дата.

Мост для остальных сущностей, который заполняется тем же способом:

| Логическое имя | Объект Multy / пример системного имени | Источник и кто меняет |
|---|---|---|
| `поднял_руку` | список `hand_raised` | сервис по подтверждённому запросу условий/покупки |
| `ждёт_ответа` | список `human_wait` | сервис при передаче; человек при завершении |
| `ответ_ИИ` | временная `answer`, `{var:answer}` | результат ИИ-действия; затем валидатор и разборщик |
| `текст_события` | стандартная `{var:object.text}` | платформа текущего события, не произвольная постоянная запись |
| `оплата` | строка журнала: `event_name=оплата`, свой `event_id` | сервис после проверки платёжного события; повтор не создаёт вторую запись |
| `единица_потреблена` | строка журнала с `unit_id` | сервис по уникальному выполненному действию |
| `источник_ролик`, `сегмент`, `когорта` | отдельные постоянные поля и колонки журнала | исходный переход/данные карты; уточнение по оговорённым событиям |

Здесь примеры не заменяют полный справочник проекта: в него входят также согласия, цена, продукт, порог, поток, окно, волна, статус практикума, ссылка оплаты, сроки, последнее сообщение и все дополнительные поля выбранной воронки. События получают строку моста даже тогда, когда у них нет отдельного поля профиля.

Дату регистрации/неделю когорты, идентификатор потреблённой единицы, дедлайны и оплату сохранять как постоянные данные. Нельзя увеличивать `units_consumed` повторно за одно и то же действие. Нужен идентификатор единицы и защита от дубля в карте.

Временные переменные персональны, но живут только до выхода из ветки. Их имя — латиница, цифры, `_`; точка означает путь внутри значения. Примеры: `{var:object.text}` — текст входящего события; `{var:answer}` — сохранённый результат ИИ. Эти значения не заменяют поля клиента. Глобальные переменные общие для проекта, подходят для настроек или общих счётчиков, но не для индивидуального стопа, истории и оплаты.

**Тег методики → список Multy.** «Списки» → «Создать» → название и уникальное системное имя → «Сохранить». Например, `sales_stop`, `human_wait`, `paid_main`, `hand_raised`. В схеме выбирать «Добавить в список»/«Удалить из списка». Функция «Добавить заново, если добавлен» ведёт счёт повторных добавлений; по умолчанию не использовать её как журнал уникальных действий.

## 4. Таймеры, очереди и приоритет событий

В контейнере «Запустить таймер» выбрать формат: «Относительный», «Завтра или позже в указанное время», «Конкретное дата и время», «Несколько секунд», «Дата и время из поля» или «Дата и время из переменной». Один день относительного таймера — 24 часа. Поле даты/времени хранит UNIX-время. Есть смещение времени, расписание работы блока и название таймера.

**Решение сборки:** дать таймерам имена по назначению и продукту: `series_main`, `offer_main`, `link_main`, `human_wait`; конкретные имена зафиксировать в справочнике. Не складывать выдачу оплаченного доступа и продажные напоминания под одно имя. Контроль перед каждой отправкой: стоп, оплата именно этого продукта, передача человеку, последнее сообщение, дедлайн. Эта повторная проверка нужна и после таймера.

«Отменить таймеры и ожидание событий» умеет выбирать ID контейнеров, названия таймеров, ID стартового события. Один ID стартового события отменяет последующие таймеры этой ветки **для данного пользователя**. Опция «Удалять также ожидания событий и кнопок» снимает промежуточные ожидания и возможность срабатывания старых кнопок. Есть отдельное действие «Отменить ожидание событий и кнопок» с выбором текущей или другой схемы.

| Пришедшее событие | Сначала записать | Затем отменить | Что остаётся |
|---|---|---|---|
| `/stop` / подтверждённая отписка | постоянный стоп и исключение из рассылок | все автоматические сообщения, охваченные стопом, и ожидания продаж | право на оплаченный продукт сохраняется; ответ на самостоятельное обращение — по карте |
| подтверждённая оплата | покупку, заказ, продукт, сумму/статус | продажу и напоминания оплаченного продукта | выдача доступа и необходимый сервис покупки; при стопе без продаж |
| передача человеку | `human_handoff = 1`, очередь живого ответа | ИИ, продающие ожидания и касания по карте | уведомление человеку, дежурный ответ сервиса |

При совпадении `/stop` и оплаты доступ выдаётся, продажные сообщения не возобновляются. Отмена таймеров не равна отмене отдельной массовой рассылки: её исключения и состояние проверять отдельно. Нет подтверждения транзакционной блокировки гонки «таймер уже исполняется → пришла оплата»; это обязательный тест. Если перед отправкой нельзя надёжно остановить касание, автопродажу не запускать.

## 5. ИИ и служебные метки

Официальная минимальная схема: «Входящее сообщение» → действие «Создать сообщение через нейросеть» (вкладка «Интеграции») → сохранить ответ в `answer` → «Отправить сообщение» с `{var:answer}`. Для ГККД этот пример **не готов**: прямой вывод `answer` покажет служебные метки и обойдёт проверки оплаты/стопа/передачи.

В ИИ-действии выбираются платформа, модель, интеграция, Prompt/инструкции и сообщение пользователя (обычно `{var:object.text}`). Без выбранной интеграции расходуется баланс нейро-рублей Multy; со своей интеграцией — баланс провайдера, плюс сообщения Multy. Это выбор человека, а не обещание бесплатного ИИ.

История передаётся JSON-массивом. «Добавить входящее сообщение в историю ассистента» поддерживает роли пользователя и ассистента и ограничение количества сообщений/экономный режим. Временный результат нужно пересохранять в JSON-поле профиля; иначе следующий вход из другой ветки его потеряет. Историю сервисных сообщений тоже дописывать, чтобы ИИ знал о выданной ссылке, оплате и передаче.

**Решение сборки:** сервис проверяет `согласие_пдн = да`, а в нише здоровья также `согласие_здоровье = да`, и отсутствие `human_handoff` → загрузка разрешённых фактов и постоянного контекста → запрос ИИ → проверка успеха → разбор результата → действие сервиса → безопасный текст человеку. Отказ, неясный ответ или пустое значение любого требуемого согласия ведут в служебную ветку без передачи сообщения и истории провайдеру. Проверка обязательна на каждом входе; новая ветка и повторный старт не выставляют согласия. Действия «Поиск в тексте по регулярному выражению» и «Замена в тексте по регулярному выражению» позволяют извлечь/удалить метки. Но конкретное регулярное выражение, формат переносов, несколько меток, неизвестная метка и пустой текст проверяются в проекте. Реестр допустимых меток — `knowledge/bot.md`, раздел 1.2; произвольная строка не запускает действие.

Метка `##ССЫЛКА:основной##` — запрос действия, не доказательство полномочий. После неё сервис ещё раз проверяет продукт, цену, зону, условия, стоп и факт оплаты. Метка об оплате из текста клиента или ответа ИИ не подтверждает платёж. Служебная метка и резюме человеку не отправляются. При невалидном результате — предусмотренная ветка ошибки и уведомление, без необработанного вывода.

**Не найдено в тексте универсального ИИ-действия:** отдельная настройка для служебного `[КОНТЕКСТ]` со своей ролью, гарантированная обработка нашего протокола `##…##`, атомарное исполнение инструмента с оплатой. Не выдавать придуманный пункт меню за существующий. Если обязательный контракт не помещается в подтверждённые настройки, рассмотреть действие «Отправить запрос на внешний сайт» к выбранному провайдеру с явным JSON по его актуальной официальной документации. Это отдельная интеграция, согласуемые расходы и обработка данных; не считать её уже сделанной. Ключи вводятся в защищённые настройки, не в промт, файлы проекта или журнал.

## 6. Prodamus, оплата и вебхуки

Подтверждён нативный Prodamus. Последовательность из справки:

1. Проект → «Настройки проекта» → «Интеграции» → «Prodamus» → «Добавить». Ввести имя аккаунта/поддомена и секретный ключ. Секрет человек вводит сам либо через разрешённый защищённый способ; не копировать его в чат.
2. Сохранить и заново открыть интеграцию. Скопировать «Webhook URL для настройки уведомлений».
3. В аккаунте Prodamus: «Настройки» → «Настройка уведомлений» → «URL адреса для уведомлений» → вставить URL → «Сохранить». Это внешняя настройка; перед фактической сборкой должен быть подтверждён её аккаунт и назначение.
4. В Multy заранее создать продукт с согласованной ценой. В схеме событие запроса оплаты → «Создать заказ» → «Добавить продукт». Сохранить передачу интеграции в событие.
5. Действие «Создать ссылку на оплату в Prodamus» → интеграция → «Получать продукты из переменной», если заказ создан раньше; иначе указать продукт и цену → «Задать данные клиента» → «Сохранить ссылку в переменную», например `payment_url` → сообщение с `{var:payment_url}` после проверок.
6. Отдельная ветка: «Поступил новый платеж» → проверка заказа/продукта/оплаченной суммы и успешного результата → постоянная запись покупки → отмена продаж → доступ и онбординг. Если интеграция из заказа не передана, перед сообщением нужен «Переключить интеграцию».

Для тестовой ссылки справка описывает «Дополнительные параметры запроса» → параметр `demo_mode` → тип «Число» → значение `1`. Тестовые номера карт здесь не дублируются: некоторые в статье уже имеют прошедший срок, актуальные брать из официальной документации Prodamus. Человек сам вводит платёжные данные и подтверждает платёж. Тестовый webhook и настоящая оплата различаются в журнале.

**Рассрочка — по реестру условий.** Проверяется сумма, подлежащая оплате по конкретному заказу/графику, а не всегда вся цена продукта. Если утверждённая внутренняя рассрочка даёт доступ после первого взноса, его подтверждение считается оплатой основного для доступа и снятия продаж; остальные взносы остаются отдельными поступлениями того же покупателя. Произвольный недостающий платёж не заменяет предусмотренный взнос. Сумму выплаты после комиссии не путать с суммой оплаченного заказа.

Не найдено достаточного текстового подтверждения: гарантированное закрытие персональной Prodamus-ссылки по нашему дедлайну; автоматическая дедупликация webhook в нашей воронке; проверка подписи произвольного пользовательского webhook силами конструктора. Нативную интеграцию нельзя приравнивать к обработке любого входящего URL. Срок ссылки, сопоставление клиента с заказом, частичная/повторная/чужая оплата и отмена/возврат проверяются отдельными сценариями. Нельзя говорить «ссылка закрылась», если провайдер ещё принимает её.

Универсальный входящий webhook: «Вебхуки» → создать → тип контакта, источник данных, путь к контакту, интеграция → сохранить → повторно открыть и получить URL. В схеме «Входящий вебхук» + условие «Вебхук, который запустил событие». Данные доступны в `{var:request}`, `{var:object}`, `{var:platform}`. Публичный URL не является доказательством оплаты: источник должен подтверждать событие по правилам своего провайдера.

## 7. Передача человеку

«Диалоги» позволяют видеть сообщения всех ботов/сообществ и отвечать из одного окна. Раздел предварительно включается; типы сообщений настраиваются через «Настроить типы сообщений», шестерёнку проекта или «Настройки проекта» → «Уведомления». По справке каждое учитываемое сообщение расходует одно сообщение баланса. Это не бесплатный безлимитный операторский чат.

Уведомление эксперту: «Сменить чат для следующих действий» → нужный административный чат → сообщение с вопросом и резюме. Если исходное событие другой платформы, например Prodamus, сначала «Переключить интеграцию». Чат должен быть известен сервису; справка предлагает добавить туда бота, выдать нужные права, написать сообщение, затем обновить схему. Не запрашивать лишние права вне конкретной сборки.

**Решение сборки:** постоянный `human_handoff = 1` блокирует ИИ через условие на входе каждой его ветки, снимает назначенные касания, добавляет в список ожидания. Возврат человеку/администратору дать явным действием: снять флаг и список только после ответа и принятого решения продолжить. Нативный отдельный переключатель «передать оператору», автоматически выключающий все схемы и ИИ, в тексте не подтверждён. Не утверждать, что открытие «Диалогов» остановило автоматизацию. Дежурный ответ сервиса работает отдельно от ИИ по карте проекта.

Источники, проверка 01.11.2026: [диалоги](https://help.multy.ai/dialog), [сообщение админу](https://help.multy.ai/graph/examples/forward-admin-message), [заметка в диалог](https://help.multy.ai/graph/effect/core/chat/dialog-note).

## 8. Рассылки и исключения

Нативные статусы: «Черновик», «Рассылка запланирована», «Рассылка отправляется», «Рассылка отправлена». В запланированной рассылке есть «Отменить» в правом верхнем углу; справка также допускает остановку запущенной. Отмена личного таймера не доказывает исключение из массовой рассылки.

Для массовых действий через схему: «Выполнить для участников списка» → «Отправить по участникам списка» → «Исключить участников списков» → типы профилей → бот-отправитель. Можно включить «Выполнить по таймеру» с UNIX-датой. Стоп, оплаченный продукт, передача человеку и «последнее сообщение» должны исключать продажи независимо от способа отправки. Исключения — часть каждой конкретной рассылки, а не пожелание в промте.

Тест нативной рассылки: «Пользователи» → свой профиль с соответствующим контактом/ботом → «Привязать к админу» → сохранить рассылку → «Тестировать». Если кнопки нет, сверить ботов и привязку; не отправлять на базу вместо теста. Массовый запуск/публикацию подтверждает человек после предпросмотра состава аудитории и текста.

Источники, проверка 01.11.2026: [статусы и отмена](https://help.multy.ai/mail/mailing-statuses), [тестирование](https://help.multy.ai/mail/mailing-testing), [действия по списку и исключения](https://help.multy.ai/graph/effect/core/timer/branching-schedule).

## 9. События, аналитика и когорты

Для журнала ГККД применима «База данных»: создать базу → шестерёнка → колонки с системными именами → «Добавить строку в базу данных» в нужных ветках схемы. Обязательные поля по `knowledge/improvement.md`, §2: `event_id`, `person_id`, `event_name`, `occurred_at`, `timezone`, `product_id`, `cohort`, `flow_version`, `source`, `segment`; для потребления — `unit_id`, для заказа/платежа — связанные `order_id`/`payment_id` и сумма/валюта/статус. Если платформа/выгрузка использует `user_id` или `cohort_week`, в справочнике явно сопоставить их `person_id` и `cohort`; разные контакты не объединять без основания. Идентификатор человека — устойчивый и минимальный для сопоставления, без лишних контактных данных. Уникальность `event_id` и отсутствие дублей — решение сборки, не заявленная гарантия действия добавления строки. Не сохранять лишнюю переписку и секреты в аналитический журнал.

В актуальной статье «Аналитика» есть «Создать дашборд» → название → ОК → «Добавить виджет» → тип → источник данных → показатель/агрегация → измерения/фильтры → период → «Сохранить». Источники включают заказы, сделки, задачи, рассылки, страницы, рекламные каналы, пользователей, историю значений.

«Воронка по блок-схеме» считает уникальных пользователей, проходивших выбранные блоки: выбрать схему → блок → название шага; до 50 шагов, рекомендуют до 10. Это не воронка этапов CRM-сделки. Для денег по источнику выбирать «Заказы»/«Сделки» и измерение «Источник», а не «Рекламные каналы» (там посещения).

Старый пример «Аналитика по каждому шагу» предлагает глобальный JSON-счётчик и прямо запрещает считать им повторные прохождения. Его обещание будущего раздела аналитики уже перекрывается текущей большой статьёй; не выбирать его базовым учётом.

**Не найден готовый когортный отчёт ГККД** «неделя входа → оплаты на 30/60/90-й день» и кривая «потребление → оплата» с нужной связкой пользователей и покупок. Хранить исходные события/дату когорты и считать по выгрузке, либо настроить виджеты после проверки возможностей фильтра конкретного аккаунта. Выручка за календарный месяц не заменяет зрелую когорту. Формулы виджета работают по одним и тем же строкам; произвольное сравнение разных выборок не обещать.

Источники, проверка 01.11.2026: [базы данных](https://help.multy.ai/database), [добавление строки](https://help.multy.ai/graph/effect/program/database/row-add), [актуальная аналитика](https://help.multy.ai/analytics), [старый счётчик и ограничение повторов](https://help.multy.ai/graph/examples/analitika-po-kazhdomu-shagu).

## 10. Комментарий → личка: граница аналога ChatPlace

Подтверждено событие «Комментарий создан» для Telegram и ВКонтакте. Условия: ID поста, текст комментария, текст поста, канал. В Telegram ответ на чужой комментарий классифицируется уже как «Входящее сообщение в чате». Для ВК есть пример приёма домашних заданий в комментариях: сохранить ID созданного поста → ловить комментарий под ним → список/другие действия.

**Решение сборки:** событие комментария → проверка нужного поста и кодового слова → определить пользователя → условие «Разрешено отправлять сообщения» для нужного бота/сообщества → при разрешении выбранная личная ветка; иначе публичный корректный ответ со ссылкой запуска бота и продолжение только после действия человека. Действие отправки проверять на адресата: комментарий не должен случайно получить личный текст.

Не найдено подтверждение Instagram/Reels-триггера и точного аналога всех функций ChatPlace; нет гарантии, что TG-бот может первым написать незнакомому автору комментария. Нельзя обещать «любому комментатору автоматически в личку». До включения проверить три случая: человек уже запускал бота; никогда не запускал; запретил сообщения. Комментарий, ответ на комментарий, повторное слово и дубль события тестировать отдельно.

## 12. От build-scheme.md к сборке в браузере

Конструктор готовит `06-bot/build-scheme.md` по шагам 0–15 из `knowledge/bot.md`, сохраняя нумерацию. Это инструкция конкретной сборки Multy, а не общий список функций. Для каждого шага: файл-источник → объект платформы → реальный пункт интерфейса → параметры → ожидаемый результат → проверка → запись в журнал.

Перед работой проверить актуальный экран и официальную статью. Названия верхних групп в справке встречаются в разных вариантах: «Автоматизация» → «Блок-схемы», «Пользователи» → «Поля профилей», «Настройки проекта» → «Интеграции». При отличии UI не угадывать скрытую кнопку: зафиксировать фактический путь в журнале. Один источник не даёт права назвать любой несовпадающий экран ошибкой сервиса.

1. **Вход и изоляция.** Человек входит в нужный аккаунт. Сверить проект и бота. До теста выбрать тестовую интеграцию; не привязывать черновик к рабочей базе. Проверить тариф и бесплатные контакты. Ничего не оплачивать и не публиковать в рамках подготовки.
2. **Мессенджер.** «Настройки проекта» → «Интеграции» → нужная платформа → подключить по официальной статье. Токен/разрешения вводит человек защищённым способом. Тестовый пользователь пишет боту; входящее сообщение появляется в «Пользователях»/«Диалогах». Для TG: [официальное подключение](https://help.multy.ai/integration/tg/integration-telegram), проверено 01.11.2026.
3. **Постоянные объекты.** Создать поля и списки из согласованного справочника. Создать продукты и базу событий. Проверить тип каждого поля и системное имя. Экспортировать соответствие в схему.
4. **Каркас.** «Автоматизация» → «Блок-схемы» → «Добавить схему»; создать события, условия, сообщения, действия и таймеры; в настройках «Разрешенные интеграции» выбрать тестового бота. Создавать контейнер выбором конкретной функции, соединять порты по карте. Назвать блоки ID из `05-state-map.md`. Стрелку «Иначе» тоже обработать.
5. **Детерминированные ветки первыми.** Собрать согласие (шаг 5), серию, запись, отказ, `/stop`, оплату и передачу. Вставлять утверждённые сообщения из `06-texts/`, документы и цену из реестра `03-product-facts.md`. Не переписывать цену из памяти. Имена таймеров, ID стартовых событий и исключения занести в справочник.
6. **ИИ после защитных проверок.** Настроить действие, историю и разбор меток по разделу 5. На входе проверить согласие/передачу, перед действиями — бизнес-условия. Тест невалидного результата выполнить до прямого общения с клиентами.
7. **Платёж и человек.** Собрать по разделам 6–7, проверить уведомление эксперту и подтверждённый платёж в изолированном режиме. Доступ выдать только по совпавшей покупке. Все тестовые последствия явно пометить.
8. **Учёт.** Каждая точка карты добавляет строку события. Создать минимальный дашборд и сверить его с фактическими строками. Дубли одного события не должны давать второй доступ или второе потребление.
9. **Сохранение и тест.** Сохранить схему; включить только согласованный тестовый контур. Пройти `test-dialogs.md` и чек ниже, приложить наблюдаемые доказательства. Историю «Пользователь уже проходил блок однажды» нельзя обнулить — повторный тест этого условия требует свежего тестового контакта или специально подготовленного нового сценария; не считать кнопку сброса полей сбросом всей истории.
10. **Финиш.** Записать что создано, что включено, где проверено и что блокирует запуск. Человек подтверждает оплату и публикацию/рабочее включение после просмотра конкретного результата. Агент делает доступные разрешённые действия, затем проверяет факт; отсутствие доступа к браузеру не скрывается за словом «собрано».

## 13. Приёмка и assembly-log.md

Минимальный чек дополняет все сценарии `test-dialogs.md`:

- Правильные аккаунт, проект, разрешённая интеграция и тестовый контакт; рабочая база не затронута тестовой отправкой.
- Все требуемые согласия записаны до ИИ; сценарий 0 из `knowledge/bot.md` подтвердил отсутствие вызовов при отказе/пустом значении, включая согласие на здоровье в соответствующей нише. После новой ветки сохранены история, согласия, стоп, оплата, передача и когорта.
- Все метки из реестра разбираются, не видны клиенту; неизвестная/повторная/поддельная метка не запускает продажу или оплату.
- Оплата снимает личные таймеры и массовые продажи оплаченного продукта; повтор webhook не выдаёт второй доступ. Чужой/отменённый платёж и сумма ниже предусмотренного взноса не подтверждают покупку; согласованный первый взнос рассрочки обрабатывается по разделу 6.
- Оплаченный вход не помечает основной оплаченным; смена состояния/повторный старт не возвращают продажу купленного продукта и не меняют когорту первого входа. Флаги контекста сверены с ID текущего продукта.
- `/stop` снимает отправки и ожидания; совпадение стопа/оплаты сохраняет доступ без продаж. Проверены таймер непосредственно перед отправкой и уже ожидающая кнопка.
- Передача уведомляет нужного человека; ИИ и назначенные касания остановлены; дежурный сервисный ответ работает; возврат явный.
- Дедлайн реален у платёжного провайдера. Ни одного касания в момент закрытия и позже. «Последнее сообщение» запрещает повторную продажную постановку любым входом.
- Рассылка имеет актуальные исключения и тест на себе; никакая массовая отправка не использована как тест.
- Комментарий проверен для известного/нового/запретившего сообщения пользователя и для ответа на чужой комментарий.
- Журнал совпал с контрольными действиями; когортный отчёт не подменён календарной выручкой.
