# Команды направлений

## 1. Назначение и старшинство

Иерархия: главный Фиксик (`root`) → координатор нужного направления → специалисты существующих ролей.

Это слой распределения работы над общим проектом; двенадцать ролей `agents/00`–`11`, их полные методички, пять развилок и контракты `core/handoff.md` сохраняются.

Старшинство источников — `core/handoff.md`, §3.10; настоящее правило уточняет распределение команд, не переносит выбор человека или владение каноническими файлами координатору.

Фиксик выбирает только нужные команды: `strategy`, `nurture`, `sales`, `launches`, `delivery`, `growth`.

Профиль из `teams/<id>.md` читается при назначении направления, а не весь каталог сразу.

Малую задачу Фиксик вправе отдать прямо специалисту без координатора и дополнительного журнала команды; обязательные проверки при этом сохраняются.

Координатор отвечает за декомпозицию, зависимости, сбор короткого результата и передачу блокеров, а не становится новым Продуктологом, Архитектором или автором текстов.

Координатор читает собственный профиль, общие правила и полный контракт только назначаемых ролей из `core/handoff.md`, §4, их разделы формата результата и полные методические карточки, нужные для текущей приёмки.

Весь производственный промпт и его обязательные методики читает сам исполнитель; координатор обращается к дополнительным разделам при конкретной неоднозначности, а не дублирует чтение всех исполнителей заранее.

Диагност, общение с человеком, все пять развилок и разрешение конфликтов остаются непосредственно у Фиксика.

## 2. План запуска и единственный писатель

Для составной задачи Фиксик до запуска команд утверждает план распределения файлов в `<проект>/00-team-board.md`; малый прямой вызов специалиста отдельной доски не требует, но его файлы не должны пересекаться с активными заданиями.

Только Фиксик создаёт и изменяет эту доску; команды возвращают заявки на её изменение в отчёте.

Доска хранится в приватном проекте эксперта, не в библиотеке и не вместо паспорта.

Минимум доски:

| Пакет / команда | Цель и режим | Исполнитель / роль | Зависит от | Входы / SHA | Выданные файлы / границы роли | Статус / блокер | Проверки / следующий шаг |
|---|---|---|---|---|---|---|---|

Для каждого активного задания указываются ID, версия пакета, текущий владелец записи и явный момент освобождения файлов после завершения или остановки исполнителя.

Доска — изменяемое состояние управления, а не неизменный вход материала: перед записью проверяют текущие ID/версию задания, паузу, назначенного владельца, границы `writes`, зависимости и занятость файлов.

SHA доски сохраняет происхождение пакета, но изменение статуса другой задачи или переход своей задачи из ожидания в назначение не инвалидирует содержательные входы автоматически.

Изменение полномочий, владельца, состава задания, паузы или зависимости блокирует затронутую работу до решения Фиксика; неизвестную дельту доски нельзя молча считать служебной.

Фиксик описывает разрешённые переходы своей задачи в пакете, а исполнитель сверяет изменившиеся поля; хеши фактуры, условий, карты и самих материалов проверяются отдельно строго.

Нельзя одновременно выдать один файл двум писателям, включая специалистов общей роли из разных команд, журнал команды, служебный файл или разные строки паспорта.

Разделы паспорта по `core/handoff.md` сохраняют своих владельцев; запись в один `00-passport.md` сериализуется Фиксиком целиком, хотя каждый специалист меняет только разрешённые ему строки.

На время такой записи Фиксик тоже не пишет в паспорт; он принимает отчёт и обновляет свои строки после освобождения файла.

Чтение и независимая работа над разными файлами допустимы параллельно, если входы актуальны и зависимости закрыты.

План координатора — предложение до подтверждения Фиксиком; самовольное назначение нового писателя, нового пути или передачи владения запрещено.

Одна и та же роль может обслуживать несколько команд последовательно либо писать разные выданные файлы; это не основание создавать копии канонических результатов.

### Каноническое владение

| Объект | Единственный владелец по роли | Действие команды |
|---|---|---|
| `03-product-facts.md`, условия и ID | Продуктолог | Заявка через Фиксика; затем использовать принятую версию |
| `05-state-map.md`, общие состояния, очереди, события | Архитектор | Заявка через Фиксика с затронутыми переходами |
| `05-funnel.md`, включая единственный список материалов п. 7 | Архитектор | Предложить материалы/драматургию; не вести альтернативный список |
| Остальные файлы и строки паспорта | Владельцы `core/handoff.md`, §4 | Запись только своей роли и по утверждённому плану |
| `00-team-board.md` | Фиксик | Только заявка/отчёт |
| `<проект>/teams/<id>.md` | Назначенный координатор этого направления | Только частный журнал своей команды |

Журнал команды содержит ссылки, входные SHA, выданные пакеты, решения Фиксика, результаты, блокеры и дельту; канонические материалы в него не копируются.

Минимальная запись журнала:

| Пакет / версия | Входы / SHA | Решение Фиксика / выданные файлы | Специалист / зависимость | Результат / SHA / проверка | Блокер / дельта / следующий шаг |
|---|---|---|---|---|---|

Шапка журнала следует `core/handoff.md`, §2: агент — координатор направления, входы — фактический пакет; статус отражает его готовность, а не утверждение канонических результатов.

Не путать приватный `<проект>/teams/<id>.md` с одноимённым профилем библиотеки `<корень>/teams/<id>.md`: рабочий запуск не изменяет библиотеку.

Специалисты не пишут в журнал координатора; передают ему отчёт, а свои артефакты оставляют на назначенных путях.

## 3. Входной пакет

Фиксик передаёт координатору один проверяемый пакет, совместимый с `core/handoff.md`, §7.1 и `knowledge/fiksik.md`, §5.1:

1. ID/версия задания, команда, цель, режим, критерий готовности и граница текущего этапа.
2. Полные пути корня системы, приватного проекта и корня методичек; точные промпты ролей и полные обязательные разделы методик по их режиму; маршрут и закреплённые ревизии компонентов из `integrations/components.md` и `dependencies.json`.
3. Входные файлы и разделы с версиями и SHA-256 фактических байтов; источники с датами, исходными ID цитат/утверждений и статусами доказательств; существенные пробелы.
4. Принятые выборы человека с датой/ссылкой на `00-dialog.md`, актуальные ID/версия условий, ограничения паспорта; что можно исправлять и какой выбор нельзя менять без развилки.
5. Действующие полномочия: разрешённая локальная работа, предел внешних действий, доступные инструменты/контексты и отсутствие нужного доступа без секретных значений.
6. Утверждённый Фиксиком план: специалисты, конкретные файлы, разрешённые строки/разделы, зависимости и порядок записи общих файлов, включая паспорт.
7. Уже выполненные проверки с охватом/SHA и счётчиками кругов, открытые находки/ID, оставшийся лимит исправлений, основания остановки и ожидаемый следующий получатель.

Номер версии не заменяет проверку байтов; одинаковый SHA не доказывает свежести внешнего источника.

Координатор передаёт специалисту достаточный адресный пакет по его полному промпту, без повторного интервью и выбора продукта, копирования архива или сокращённого пересказа обязательной методики.

Если пакет неполон, координатор возвращает точный блокер Фиксику; независимо доступная подготовка продолжается только в выданных границах.

## 4. Общая очередь и границы направлений

У одного человека один актуальный путь и одна совместимая цепочка по `05-state-map.md`; названия команд не создают отдельные лимиты уведомлений.

| Команда | Зона заявки на общую карту | Передача соседям |
|---|---|---|
| `nurture` | Вход, согласие, магнит, серия, потребление, порог, практикум | Подтверждённая готовность/поднятая рука → `sales`; регистрация на выбранное событие → `launches` |
| `sales` | Предложение, квалификация, диалог, заявка, оплата, реальное окно и одна повторная волна | Оплата → `delivery`; отказ → разрешённый канал без нового дожима; event-связанные сообщения согласует с `launches` |
| `launches` | Регистрация, напоминания, присутствие/просмотр, запись, календарь события/28 дней | Запрос условий/покупки → общий путь `sales`; оплата → `delivery`; участнику живого запуска отключается несовместимая автоцепочка |
| `delivery` | Доступ, онбординг, выполнение, помощь, контрольная точка, отзыв, следующая ступень | Новое согласованное предложение → `sales` по правилам карты; недовольному сначала помощь человека |

`strategy` задаёт предложения по исследованиям/продукту/пути через владельцев, а `growth` предлагает измеренные исправления всех зон; обе команды не запускают собственную рассылку.

Спор о принадлежности материала, наложении таймеров или владельце следующего контакта решает Фиксик; принятую логику записывает только Архитектор, реализацию — назначенные владельцы.

Заявка Архитектору идёт через Фиксика: исходный SHA карты, состояние/событие/ID материала, причина, вход/выход, тайминг, кому доступно, что отменяется, частота, метрика и затронутые команды.

Материал без ID в `05-funnel.md`, п. 7 не добавляется самовольно; кандидат на добавление возвращается Фиксику для Архитектора.

Приоритет глобальных событий сохраняется по `agents/05-architect.md`, шаг 6: `/stop` и стоп-метки > оплата > передача человеку; дальше — остальные события действующей карты.

Стоп отменяет автоматические цепочки всех направлений; достоверное финансовое событие оплаты всё равно фиксируется и обслуживается, снимая продажи купленного; стоп запрещает рекламные сообщения, но не теряет платёж.

Доступ и необходимая служебная помощь идут разрешённым по карте способом без включения рекламных очередей.

Передача человеку снимает несовместимую автоматизацию и оставляет реального ответственного и часы ответа; ни одна команда не продолжает параллельный дожим.

Частота считается суммарно по всем очередям: по таймеру не чаще одного сообщения в день, кроме уже разрешённых исключений реального срока; ответ на действие человека учитывается по `knowledge/follow-up.md`, §0.

Прямой вопрос о цене получает честный ответ и до порога; он не включает автоматическую продающую цепочку без предусмотренного сигнала/согласия.

Неизвестный просмотр не становится фактом потребления; отказ, последнее сообщение и стоп нельзя обойти сменой команды, потока или названия цепочки.

## 5. Проверки и короткий возврат

Координатор проверяет полноту передачи и выполнение заданий; его самопроверка не даёт независимый допуск.

Фиксик отдельно назначает предметный source/editor review по `core/handoff.md`, §7.1, Клиента мечты и Контролёра; координаторы не запускают их автоматически внутри каждой команды.

На комплект каждого предусмотренного этапа приходится ровно три последовательных общих круга Клиента мечты с исправлениями владельцев и повторным чтением всего комплекта, а не три круга на команду, материал или компонент.

Зачёт охвата и чистый пакет читателю — по `core/handoff.md`, §7.2; новый фактический вид страницы, слайда, бота, записи или видео требует своего охвата и не наследует допуск сценария автоматически.

Для одного и того же результата предметное ревью ограничено тремя кругами; Контролёр сохраняет два круга на находку, связанные находки делят лимит.

Переименование задания, новая команда, версия или сессия счётчик не обнуляют; пределы разных проверок не складываются и не заменяют друг друга.

После исчерпания лимита блокер возвращается Фиксику/владельцу/человеку без зависимой передачи; неблокирующий остаток требует явного решения, владельца и основания.

Специалист возвращает отчёт координатору; в рамках заранее выданного пакета и плана координатор самостоятельно запускает специалистов и локальные исправления в применимых лимитах, без нового утверждения каждого внутреннего вызова.

Фиксик получает стартовый план/пакет, существенный блокер или запрос изменения канона и итоговую приёмку; отчёта после каждого шага не требуется, подробности остаются в журнале команды.

Координатор возвращает короткий отчёт, не полный текст материалов:

- ID пакета, результат относительно критерия, фактический статус: подготовлено / заблокировано / ожидает проверки или данных.
- Артефакты: пути, роли-владельцы, версии/SHA, ссылки на фактически выполненные проверки и ограничения их охвата.
- Дельта: изменённые ID условий/событий/материалов, значения до → после, затронутые потребители и представления; отдельно подтверждённое отсутствие смысловых изменений.
- Блокеры/остаток: что требуется, у кого, какая зависимость остановлена; запрос на развилку без самостоятельного изменения выбора.
- Заявки Фиксику: изменение доски, Архитектору/Продуктологу/другому владельцу, необходимые проверки и следующий пакет.

Готовность координатора означает проверяемую передачу в рамках этапа; она не означает независимый pass, собранную поверхность, публикацию или доказанные продажи.

## 6. Возобновление, пауза и исполнение

Перед продолжением координатор сверяет входные и выходные SHA с последней принятой записью, полномочия, выборы, открытые находки и занятость файлов на доске.

Изменение входа останавливает затронутую зависимую работу: координатор сообщает дельту/потребителей, Фиксик отмечает устаревание по `core/handoff.md`, §6–7.3 и выдаёт новую версию пакета владельцам сверху вниз.

Актуальные незатронутые исследования и материалы используются повторно; отзыв на другие байты не переносится молча, механическое изменение подтверждается отдельной проверкой дельты.

Команда «пауза» прекращает производство и запрещает новые задания и содержательные правки; разрешена только служебная запись состояния остановки в своём журнале и Фиксиком на доске: координатор отменяет/останавливает уже запущенных специалистов доступными средствами, сообщает подтверждённый статус каждого Фиксику и сохраняет возможность восстановления без продолжения производства.

Если отмена технически не подтверждена, Фиксик оставляет файлы занятыми до фактического завершения и не выдаёт их второму писателю; результат пришедшего после паузы запуска не принимается автоматически.

Возобновляет работу Фиксик после явного снятия паузы, сверки SHA и нового назначения; время ожидания не является разрешением.

Глубина исполнения ограничена одним уровнем: координатор → специалисты; специалисты не создают координаторов, команды или собственные управляющие цепочки.

Если среда не поддерживает вложенные вызовы, координатор готовит пакеты и зависимости, а Фиксик сам запускает специалистов по утверждённому плану и возвращает фактические отчёты координатору.

Нельзя описывать подготовленный пакет как состоявшийся вызов; без отдельных контекстов действуют ограничения `knowledge/fiksik.md`, §5.3 и независимый допуск остаётся открытым.

Локальная приёмка контракта допускает один возврат специалисту с полным списком недочётов; если повторный результат не выполняет контракт, координатор возвращает блокер Фиксику, а не запускает третий такой же проход.

Этот предел не отменяет отдельные предусмотренные циклы предметного review, Клиента мечты и Контролёра; новая находка не служит способом обнулить уже исчерпанный лимит связанной ошибки.

Повторная попытка исправления требует конкретной находки, владельца и проверки результата; бесконечное планирование, новые обзоры без дельты и повторение бесплодных запусков не заменяют решение блокера.

Рабочие файлы остаются локально в приватном проекте; публикация, оплата, отправка сообщений, внешняя сборка или иное внешнее изменение допускаются только в пределах текущей авторизации через Фиксика.

Экономию времени/вызовов/токенов заявляют только по сопоставимому замеру `knowledge/context.md`, §5; сама иерархия команд измеренного улучшения не доказывает.
