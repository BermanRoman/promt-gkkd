# Горячие клиенты каждый день

ГККД Романа Бермана помогает собрать воронку продаж под работу и возможности эксперта.

На входе — чем человек занимается, его материалы, условия и текущие продажи; на выходе — папка проекта с продуктом, текстами, страницами, сценарием бота и порядком сборки.

При подходящем формате добавляются вебинар, тексты слайдов и календарь запуска; после реальных данных система разбирает просадки и готовит изменения.

Главный Фиксик ведёт человека, координаторы отвечают за направления, исполнители готовят конкретные результаты.

Двенадцать существующих ролей сохраняют предметную ответственность; шесть направлений подключаются по задаче.

Для простой правки Фиксик обращается сразу к исполнителю.

При составной работе координатор собирает задания и исправления внутри направления; общий результат, развилки и независимые проверки остаются у Фиксика.

Роли не размножаются в постоянные штаты: один профиль может обслуживать разные команды с разными границами записи.

Правила владения файлами, передачи, остановки и возобновления — в [контракте команд](core/teams.md).

## Начать или продолжить

Нужна агентная среда с доступом к локальным файлам и Git; для скриптов проверки — Python 3, для независимых отзывов — отдельные контексты/исполнители.

Выбранная модель, приложение, доступы и подключения пользователя сохраняются.

Назначь рабочую папку и передай агенту:

> Установи https://github.com/BermanRoman/promt-gkkd в этой рабочей папке по INSTALL.md; используй подходящие существующие клоны зависимостей, сохрани мои файлы и начни работу по Фиксику.

Если библиотека уже есть, достаточно: «Продолжаем ГККД» с указателем на проект; Фиксик восстановит паспорт и незавершённый этап.

Для обновления — «Обнови систему»; [INSTALL.md](INSTALL.md) сохраняет рабочие данные, проверяет версии и не обновляет все зависимости до случайного нового main.

Агент собирает данные один раз, предлагает готовые варианты и ведёт пять содержательных развилок: профиль, направление, продукт, предложение для аудитории и путь покупателя.

Уже принятые решения не спрашиваются заново без изменения основания.

| Компонент | Назначение в ГККД |

| [HVCO](https://github.com/BermanRoman/promt-hvco) | История-магнит с выполненным бесплатным обещанием; собственная структура и проверка языка |
| [Клип-лендинг](https://github.com/BermanRoman/prompt-clip-landing) | Пять связанных страниц по фактуре героя и конкретному следующему действию |
| [Копирайтинг](https://github.com/BermanRoman/promt-copywriting) | Полные нужные карточки инфостиля; восприятие на слух только для произносимого текста |
| [СПИН-вопросы](https://github.com/BermanRoman/prompt-spin-questions), [ядро СПИН](https://github.com/BermanRoman/promt-source-life) | Диагностика и продающий диалог по профильным ролям |
| [SEO/GEO](https://github.com/BermanRoman/promt-seo-geo) | Отдельная система сайта со своими инструкциями и фактической приёмкой |

Точные версии четырёх модернизированных компонентов — в [dependencies.json](dependencies.json), входы и адреса полных разделов — в [адаптере](integrations/components.md).

Компоненты получают уже собранную фактуру, не начинают повторное интервью и не создают ещё один полный конвейер согласований внутри ГККД.

Истории и тексты используют данные эксперта и клиента мечты; голос Романа, Васька из Motion и редактор сценариев не подключаются автоматически.

Локальные [инструменты](scripts/README.md) сверяют закреплённые байты и извлекают полные разделы без модельного пересказа; они не вызывают модели и не публикуют материалы.

```sh
python3 scripts/check_structure.py
python3 scripts/check_dependencies.py --repos-root /absolute/path/to/repos --route audience
python3 -m unittest discover -s tests -p 'test_tools.py' -v
```

Незакреплённые дополнительные системы и реальные аккаунты этими командами не проверяются.

## Проверка результата

Три последовательных круга Клиента мечты сохраняют полный охват этапа и помогают обнаружить непонятное действие или ложное ожидание.

Один подходящий отзыв учитывается один раз в общем реестре; поверх него не запускаются ещё три одинаковых круга текстового компонента.

Проверка фактов и Контролёр остаются отдельными: реакция синтетического читателя не подтверждает достоверность источника, удобство ещё не собранного сайта или будущие продажи.

Изменения возвращаются владельцам, затрагивают использующие их материалы и фиксируются по версии/хешу; неизменённое не переписывается заново.

Материалы, собранная поверхность и фактически проверенный результат отмечаются отдельно.

Для бота применяется адаптер Multy, сайт передаётся отдельному SEO/GEO; доступность функции и нужные полномочия проверяются перед действием.

Вход в аккаунты, оплата и публикация выполняются по действующему поручению; отсутствие инструмента не превращает схему в работающую воронку.

Проверки модернизации и границы замеров описаны в [отчёте](docs/migration.md).

Изменения командной организации, найденные конфликты и фактический прогон передачи — в [отчёте команд](docs/teams-verification.md).
