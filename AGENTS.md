# Работа с ГККД

Это библиотека методологии и агентного процесса воронки, а не запущенная воронка или обещание продаж.

При обычной работе эксперта вход — agents/00-fiksik.md, состояние — паспорт его проекта; при разработке сначала git status, актуальные decisions.md и затронутые контракты core/handoff.md.

Рабочие проекты, личная фактура и протоколы испытаний не публикуются в библиотеке; используй игнорируемый runs/ либо отдельную папку проекта.

Сохраняй полные методические карточки, двенадцать зон ответственности, пять развилок, реестр условий продукта, драматургию, вебинары/запуски и отдельный цикл Докрутки.

Три последовательных круга Клиента мечты из decisions.md §26 сохраняются; два круга Контролёра на находку — отдельное правило, их нельзя подменять общим лимитом соседнего компонента.

Роли не означают обязательного создания двенадцати контекстов для простой правки; обязательные независимые проверки не выдавай за самопроверку.

Организация направлений — `core/teams.md` и шесть профилей `teams/`; это канон иерархии Фиксик → координатор → исполнители по решению §29, а не ещё шесть обязательных вызовов на каждый шаг.

Сохраняй единственных владельцев общих условий и карты состояний; записи общего паспорта сериализуются, независимые проверки назначает главный Фиксик вне производящих команд.

Оптимизация сохраняет качество: один сбор исходных данных, адресное чтение полных нужных разделов, повторное использование проверенного неизменного, расчёты и сравнения скриптом.

Внешний компонент внутри ГККД получает готовое задание и не запускает новое интервью, выбор продукта или отдельную управляющую цепочку поверх Фиксика.

Используй проверенные версии зависимостей; чистый git status и совпавший HEAD не заменяют сравнения байтов используемых файлов с закреплённым коммитом.

Методички Романа в соседних репозиториях не переписывай автоматически; подтверждённую несовместимость исправляй в адаптере, сохраняя происхождение данных и более позднее прямое решение автора.

Не меняй выбранную модель основного чата, доступы и подключения; локальная конфигурация среды определяет модели исполнителей, переносимая библиотека не навязывает устаревший каталог моделей.

Перед выпуском: структурная и применимая инструментальная проверка, фактический синтетический прогон передачи/правок, отдельное ревью и проверка Git после push по поручению автора.

При обновлении по источникам фиксируй фактическое покрытие текста и графики; выборка страниц не считается полным разбором предоставленного файла, а иллюстрация не заменяет первичные данные.

Серия перед открытием продаж — `decisions.md`, §31, канон `knowledge/webinars-launches.md`, §8; структура Т-6 Романа и окно по methodology §7 не меняются.

Диагностика поведения и уточнения интерфейса — `decisions.md`, §30: канон шага в `knowledge/improvement.md`, §4–5, фактической поверхности в `knowledge/visual.md`, §8; не создавай поверх них новую анкету или дополнительные круги приёмки.

Готовность материалов, сборка и проверка реальной поверхности фиксируются раздельно; статический тест, текстовый прогон и реакция синтетического читателя не доказывают продажи или живую работу сайта/бота.
